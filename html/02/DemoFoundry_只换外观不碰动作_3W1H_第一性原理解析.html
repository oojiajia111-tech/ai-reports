方向 训练数据
💡 第一性原理核心立论

合成数据一直死在两个地方：仿真有正确的动作和严重失真的画面，视频生成有逼真的画面和靠不住的动作。这两条路各自去补自己的短板都补不动——仿真器再改也画不出真实光照，生成模型再训也给不出物理一致的动作。DemoFoundry 干脆不补，改成拆：用物理仿真产出「动作正确、画面难看」的代理视频，再训一个只负责把画面换成真的渲染器。动作标签从头到尾没被生成模型碰过，所以它还是准的。

What是什么：把「动作」和「画面」拆成两条独立可优化的产线

一句话概括这套系统的分工：物理仿真负责「做得对」，渲染器负责「看得真」，coding agent 负责「搭场景」，三者之间只用一个东西相连——代理视频。

阶段谁在干活输入输出
① 配对构建coding agent + 物理回放四个公开数据集（DROID / AgiBot World / RoboMIND / RH20T）的真实 episode1,884 对「真实视频 ↔ 代理视频」，1,522.03 分钟
② 渲染器训练视频生成模型（LoRA 微调）代理视频 + 真实视频首帧作参考图一个「代理 → 真实」的外观翻译器
③ 新场景生成coding agent 写程序 + 随机布局一张参考图 + 机器人规格 + 相机标定 + 任务指令新的（渲染后视频, 状态, 动作）三元组
④ 策略学习Diffusion Policy / π0.5渲染观测 + 对齐的仿真动作可部署策略（25 Hz 控制）

关键在阶段 ③ 的「零样本」性质：给一张参考图和一个任务指令，不需要目标场景的人类示范，也不需要人在生成过程中操作。agent 自己重建任务相关几何、组装场景、写出带位姿的程序，在物理仿真里跑出来的就是带正确动作的代理视频。

Why为什么：两个短板是互补的，所以不该分别去修

第 1 步：机器人学习要的样本，必须同时满足两个条件
一是观测要真（否则学到的视觉特征在真机用不上），二是动作要对（否则学的是一个物理上不可能的策略）。少任何一个，数据都是废的——这就是「演示」比「视频」贵得多的根本原因。
第 2 步：仿真的问题不在物理，在「照片级真实感的成本」
仿真天然给出精确的动作和状态，代价是外观。要让它看起来真实，传统做法是给每个场景做精细材质建模——这活儿的工作量随场景数量线性增长，而且永远追不上真实世界的丰富度。这是仿真合成数据十几年的老瓶颈。
第 3 步：视频生成的问题反过来——外观免费，物理不免费
生成模型能给你任何场景的照片级画面，但它生成的运动不保证物理一致，更关键的是它不吐动作标签。你可以事后用逆动力学去猜动作，但猜出来的动作误差会直接变成策略的偏差。所以「纯视频生成造数据」在需要精确动作的任务上一直不稳。
第 4 步：既然短板互补，就把它们串成流水线，让每个模块只做自己擅长的事
物理仿真出「代理视频 + 精确动作」，渲染器只做「代理 → 真实」的外观翻译。这一步是整个方法的枢纽：动作从不经过生成模型，所以它一直是精确的；渲染器只需要学「同一段运动在不同画风下长什么样」，这是一个远比「生成物理正确运动」简单的任务。
第 5 步：但渲染器要学外观翻译，就必须有成对数据
这是最容易被忽略的一环。要训「代理 → 真实」，你需要同一段运动的两种画风。他们的办法是反向构造：拿已有的真实 episode，用 agent 重建场景、在仿真里回放记录的动作，得到一段「动作相同、画面是仿真」的代理视频，于是自动获得配对。验收标准是逐视角轮廓 IoU ≥ 0.80，允许三轮修正，仍不达标就丢弃。最终 1,884 对通过。
第 6 步：剩下的瓶颈是「搭场景」这件事本身要靠人
于是引入 coding agent：让它读参考图、重建几何、调工具库（场景查询、抓取提议、逆运动学、运动规划、机器人控制）、写出可执行的位姿程序，再靠试执行来改代码。这一步把「场景工程」从人力变成了可自动化的编程任务，也是它敢叫「scalable」的原因。

How怎么做：一个 IoU 阈值、一个流匹配损失、一个成本方程

一、配对构建：0.80 这个阈值决定了渲染器的上限

流程是：SAM 3.1 出物体掩码 → 拟合桌面支撑面 → 简单物体用参数化形状经 Blender 脚本转网格、复杂资产用 SAM 3D Objects 重建 → 在 MuJoCo / DexSim 里回放记录动作 → 逐视角轮廓 IoU ≥ 0.80 才算对齐。

为什么 IoU 阈值这么重要：代理视频和真实视频对不齐，渲染器学到的就是「把 A 场景的画风换成 B 场景」，而不是「同一场景换画风」。这会直接污染动作-观测的对应关系。原文的数据也印证了这条路有多难走：初始回放接受率只有 33.1%，三轮修正后升到 39.7%，轮廓 IoU 从 0.517 升到 0.601，轨迹误差从 1.370% 降到 0.956%。也就是说，六成的真实 episode 根本没法用。

二、渲染器：只学外观，所以只需要 LoRA

两个底座都用了参数高效微调：LTX-2.5 用 rank-128 的 LoRA（121 帧），MiniMax-H3 用 rank-32 的 attention LoRA（158 帧 @ 24 fps）。主干和视觉编码器全部冻结，监督信号是同一段运动的真实视频。

这个「冻结主干」的选择和它要解决的问题一致：如果连主干一起训，模型会开始「创作」运动，动作一致性就丢了。只训 LoRA 等于给模型加了一条「换画风」的窄通道，它想改运动也没那个自由度。

三、生成：agent 写程序，随机布局，逐窗口自回归

  1. agent 重建资产、组装场景，用工具库写出位姿感知的程序；试执行失败就改代码；
  2. 随机化物体布局得到场景变体，执行得（代理视频, 状态, 动作）；失败的轨迹直接跳过；
  3. 用图像编辑模型生成参考图：布局来自代理视频首帧，外观来自给定参考图——这一步让「换场景不换风格」成为可能；
  4. 渲染器逐窗口自回归渲染长轨迹（窗口间 1 帧重叠）；
  5. 自动任务执行检查筛掉失败轨迹，合格的进数据集。

四、训练策略：为什么「仿真 + 生成」反而不如「只用生成」

这个结果很反直觉，值得单独说：真实 + 原始仿真只有 47.8% / 63.3%，而真实 + 生成数据能到 72.2% / 82.2%。加原始仿真数据几乎没增益（−1.1 / +1.1 个百分点），加生成数据提升 23.3 / 20.0 个百分点。

解释只有一个：原始仿真数据的视觉分布离真实太远，它对策略的贡献是「噪声」而不是「多样性」。而生成数据把视觉对齐了，于是它携带的动作信息才真正被用上。这条结论比任何一个涨点都重要——它说明合成数据的瓶颈从来不是「量」，是「画面对不对得上」。

数据缩放也给了明确曲线：每任务生成 25 / 50 / 100 / 200 条，π0.5 成功率 42.2% / 60.0% / 77.8% / 85.6%。200 条生成数据（85.6%）已经明显超过 50 条真实数据（62.2%），但仍需真实数据打底才到 82.2% 的混训水平——两条曲线的关系是「互补」而非「替代」。

Formula核心公式：一条执行、一条渲染、一条算钱

式 1　代理数据的产生：物理仿真给出「动作 + 状态 + 难看但正确的视频」
\[ (P,Q,A)=\operatorname{Execute}\big(E,\ p;\ C\big) \]
\(E\) 是仿真场景，\(p\) 是 agent 写出的任务程序，\(C\) 是相机标定；输出 \(P\) 是代理视频、\(Q\) 是对齐的机器人状态序列、\(A\) 是执行的动作。
说人话：这一行是整个方法的信任来源——\(Q\) 和 \(A\) 是物理引擎算出来的，不是任何模型猜的。它可能画面很假，但它「手真的抓到了、杯子真的倒了」。
注意 \(p\) 是程序而不是策略：一段可执行的位姿序列，可以随机布局后重跑无数次。这就是它比遥操作便宜的结构性原因——遥操作的成本随条数线性增长，而一段程序跑一百次只花算力。
式 2　渲染器的训练目标：条件流匹配，条件里装的全是「结构」
\[ \mathcal{L}_{\mathrm{FM}}=\mathbb{E}\Big[\big\|\,v^{\mathrm{train}}_{\theta}(z_{u},u;P,I^{\mathrm{ref}})-(z-\epsilon)\,\big\|^{2}_{\mathrm{valid}}\Big], \qquad z_{u}=(1-u)\epsilon+uz \]
\(z=\mathcal{E}(V)\) 是真实视频的隐变量，\(\epsilon\) 是高斯噪声，\(u\) 是流匹配时间；\(P\) 是代理视频（提供运动与几何），\(I^{\mathrm{ref}}\) 是参考图（提供外观）。
说人话：模型学的不是「从噪声生成一段视频」，而是「给定这段难看的代理视频 + 这张参考图，把噪声还原成这个场景的真实样子」。
两个条件各管一件事，这是全篇的设计核心：\(P\) 管「怎么动、东西在哪」，\(I^{\mathrm{ref}}\) 管「长什么样、什么颜色材质」。因为运动信息由 \(P\) 完全给定，模型没有动力去编造运动，动作一致性（PCK 97.24）才保得住。
那个 \(\|\cdot\|_{\mathrm{valid}}\) 的脚标也别放过：只在有效目标隐变量上取平均，条件帧不计入损失——和视频生成里的通行做法一致，避免模型把力气花在重建已经喂进去的东西上。
式 3　成本方程：编程是一次性投入，所以「多生成」才便宜
\[ \overline{C}(N)=\frac{C_{\mathrm{plan}}}{N}+c_{\mathrm{gen}}, \qquad C_{\mathrm{plan}}\approx \$9,\quad c_{\mathrm{gen}}=\$0.765 \]
\(N\) 是同一任务的生成条数，\(C_{\mathrm{plan}}\) 是 agent 写程序的一次性成本，\(c_{\mathrm{gen}}\) 是每条渲染的边际成本。
说人话：搭场景那 9 美元是摊出去的。生成 1 条要 9.765 美元（比遥操作还贵），生成 100 条摊到 0.855 美元，1,000 条 0.774 美元——而人类遥操作一条是 2.42 美元。
这个式子解释了为什么它的经济性只在「同一任务要很多条」时成立，也解释了为什么它必须靠 coding agent 而不是人工搭场景：\(C_{\mathrm{plan}}\) 一旦由人来做，就降不到 9 美元这个量级。

Worth值不值：把「数据贵」改写成「画面对不上」，代价是整条链更脆

它真证到的东西

1. 「只换外观」这个拆法是有效的，而且有干净的对照。同样 50 条数据，仅仿真 12.2% / 27.8%，仅生成 46.7% / 60.0%，仅真实 48.9% / 62.2%。生成数据把仿真数据的可用性抬了 3 倍多，直接追平真实数据——这是「视觉分布才是瓶颈」这个论断的最硬证据。
2. 混训增益说明它和真实数据是互补的。真实+生成 72.2% / 82.2%，比真实+仿真高 24.4 / 18.9 个百分点。加原始仿真数据几乎零增益，加生成数据涨两个档——这个对比把「数据的价值不在量而在对齐」讲透了。
3. 场景泛化是它相对仿真 DR 的真实优势。换绿色瓶子 21 vs 5、换背景色 22 vs 10、换光照 18 vs 2（30 次试验）。DR 只能随机化参数，它能把整个场景换掉，这是两种不同层级的多样性。

它的代价和疑点

  • 整条链的产率很低。真实 episode 反推代理的接受率只有 39.7%（三轮修正后），六成数据被丢掉。这不是一个小损耗——它意味着「用现成数据集造配对」这条路，实际上要消耗 2.5 倍的原始数据才能得到一份配对集。
  • 三个任务、每个 30 次试验。真机结论建立在「罐→托盘 / 叠块 / 笔入架」三个桌面任务上，每个 30 次。这足以证明方法有效，但不足以证明它在长时程、接触密集、双手协调任务上同样成立——而那几类恰恰是合成数据最该解决的问题。
  • 「接近真实数据」这句话要看清量级。它是「50 条生成 ≈ 50 条真实」，而在 200 条生成时已经超过 50 条真实（85.6% vs 62.2%）。但论文没有做「200 条真实 vs 200 条生成」的对照——真实数据的 scaling 曲线在哪、什么时候饱和，完全未知。缺失这一组，就无法判断生成数据的上限到底在哪。
  • 依赖物理回放能复现真实 episode。代理视频靠「在仿真里重放记录的动作」得到。如果真实 episode 里有仿真复现不了的接触（软物、颗粒、强摩擦），回放就失败，这条数据也就没了。换句话说，这套方法在最难的接触场景上会自动退化——而那里正是最需要合成数据的地方。
  • coding agent 的失败率没有被报告。论文报告了「自动任务执行检查」会筛掉失败轨迹，但没给筛掉的比例、没给 agent 写程序的一次成功率、也没给「程序写错了但检查没发现」的假阳性率。对一个把可靠性押在 agent 写代码上的系统，这是最关键的缺失指标。
一句话结论：它把一个老问题重新定义了——合成数据的瓶颈不是「不够真」，而是「动了之后画面对不上」。于是它不去改仿真器，也不去改生成模型，而是让两者各管一半，中间用一个「只换外观」的窄通道连起来。这条思路干净、可解释、成本算得清（0.774 vs 2.42 美元）。但要清楚它的边界：它只在「同一任务要很多条 + 场景能被仿真复现」时成立，而六成的配对产率和三个桌面任务，还撑不起「通用数据工厂」这个名头。
