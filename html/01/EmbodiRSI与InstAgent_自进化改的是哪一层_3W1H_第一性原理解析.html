一句话 自进化最难的不是"怎么改"，是"该改哪一层"
💡 第一性原理核心立论

"自我进化"这个词经常被当成一个动作，其实它是两个：改参数和改程序。这两件事解决的是完全不同的失败。机器人没把可乐送到，可能是抓取时手滑了，也可能是装载和运输之间漏了一次检查——前者要把动作练得更稳，后者要在流程里补一个条件判断。用同一种方法去修这两种失败，必然有一半无效。上科大与瞬适这条研究线做的就是把这两层分开：EmbodiRSI 在仿真里造一个"可以安全失败"的场，用当前策略的失败分布反过来决定下一轮采什么数据，把技能练稳；InstAgent 把多机协作封装成可执行的行为树，让反馈直接变成"加一个执行条件"或"加一个恢复分支"，把流程补全。前者换来的是 59.3% → 79.9% 的仿真自主成功率；后者换来的是"出发前和交付前都要检查可乐在位"这样一条能被复用、能被审查、能被回滚的规则。而这套东西真正的价值，是那条分层判据：先判断坏在技能还是坏在编排，再决定动哪一层。

What是什么：两条并行的自进化路径

团队把自己的目标说得非常朴素：换一个工位、换一批物体、或者接手一项新任务，机器人现在要重新采数据、重新训练、重新调试；希望这段适应过程越来越短。

围绕这个目标，他们拆出两个系统，改的东西完全不同：

EmbodiRSIInstAgent
进化对象操作策略的参数多机协作的程序
解决什么失败技能不稳（抓空、滑落）技能之间衔接漏了（该检查没检查）
改进载体训练数据分布 + 策略权重行为树（BT）+ 经验文档
核心机制Real-to-Sim-to-Real 闭环：协同纠错 + 自适应数据采集共享记忆诊断 + 结构/接口检查 + 重跑验证
关键约束同等轨迹预算下比较模型参数、原子技能、底层控制器全部冻结

两个系统都归到同一个概念下：递归自我改进（Recursive Self-Improvement, RSI）——让执行反馈持续推动策略或程序更新。而文章最后抛出的那个追问，才是全篇的题眼：一次纠错之后，这次改进能不能保留下来，让后续任务也受益？

先看数字，后面逐条审：

  • EmbodiRSI（仿真）：办公桌 + 家居桌，每子任务同为 400 条仿真轨迹，静态采集组 59.3%，纠错+定向采集组 79.9%——+20.6pp。
  • EmbodiRSI（真机）：三场景 14 子任务，每子任务 400 条仿真 + 10 条真实精调，83.1%；对照是每子任务 200 条纯真实示范，75.0%。
  • InstAgent：三组行为树系统（无跨任务经验 / 固定经验库 / 保留修订的经验库）对比，后者成功率最高；20 项任务各重复 2 次，每模型每配置 40 次。

Why为什么：五条公理，把"自进化"从一个动作拆成两个

公理一：改进能不能留下来，取决于它被写进了什么载体

"这次改好了" 和 "下次不用再改" 是两件完全不同的事，区别只在改进被写进了哪里。

载体自动生效？可读？可回滚？能泛化到没写下来的情形？
参数（权重）✅ 下次同类情况自动生效❌ 不知道它学到了什么⚠️ 要存 checkpoint✅ 能隐式泛化
程序（行为树）✅ 下次同类任务直接调用✅ 就是几个条件分支✅ 删掉那个节点就行❌ 只覆盖被写下来的情形
人的记忆❌ 换个工程师就没了✅➖⚠️

这张表决定了本文的全部结构：技能不稳 → 写进参数；流程有洞 → 写进程序。两者不能互相替代。

推论 1
"自进化"这个词之所以含糊，就是因为它没指定载体。说清载体，才说得清代价：写进参数得到泛化、失去可读；写进程序得到可读、失去泛化。

公理二：失败必须先归因到"层"，否则一定修错地方

这是全文最有实用价值的一条。同一个现象——"可乐没送到"——有两种完全不同的成因：

  • 技能层失败：ALOHA 装可乐时没抓稳，罐子掉了，但流程继续往下走；
  • 编排层失败：装载成功了，但在 Go2 出发前被人取走，而流程里没有"出发前再确认一次"这一步。

对第一种，你该做的是"让抓取在更多姿态下练得更稳"；对第二种，你该做的是"在流程里加一个检查"。如果对第二种去加训练数据，你会在一个完全正确的抓取上反复优化，永远修不好。

推论 2
所以真正的前置能力不是"会改"，而是"会诊断"——把一次失败定位到"技能本身不行"还是"技能之间没配合好"。这条判据可以直接用，不需要他们的系统也能用。

公理三：模型自进化需要失败样本，而真实机器人几乎不产生失败样本

这是一个非常硬的物理约束，很容易被跳过。

训练一个策略变强，需要它在会失败的状态下拿到正确的动作监督。但真实机器人上，失败是被严格避免的：人会在它要撞之前拦住、会在它抓空之前换一个位置、会在它快掉的时候接手。结果是：真实数据里几乎只有"成功的轨迹"，没有"失败后怎么救"的样本。

而示范数据还有个更根本的错位：示范走的是"标准路径"，策略实际会漂到"标准路径之外"。一次抓空、一次滑落，就把它带到了示范从未覆盖的局面；在那里它没有任何监督信号。

所以必须造一个可以安全失败的场。这就是 Real-to-Sim-to-Real 的真实作用——不是"省数据"，是"让你可以失败"。

推论 3
仿真的价值不在"便宜"，在"允许出错"。这也解释了为什么这套闭环的关键不是仿真精度，而是"失败能不能被识别并转成监督"——那才是协同纠错在做的事。

公理四：程序自进化需要一个"可编辑的结构"，而行为树正好卡在甜点区

想让程序能被反馈自动修改，它的表示必须同时满足三个条件：

  1. 可读：人能看懂"这里漏了一个检查"；
  2. 可执行：改完能直接跑起来验证；
  3. 可局部修改：加一个条件不应该影响其他分支。

三个候选表示的对比很清楚：

  • 自然语言的流程说明：可读 ✅，可执行 ❌，可验证 ❌；
  • 端到端黑箱策略：可执行 ✅，可读 ❌，可局部修改 ❌（改一处会影响全部）；
  • 行为树：可读 ✅（就是分工 + 依赖 + 交接条件 + 恢复分支），可执行 ✅（节点是已封装的技能），可局部修改 ✅（加一个条件 / 加一个恢复分支 / 调子流程顺序）。

这就是为什么 InstAgent 选行为树。不是因为它先进，是因为它是唯一同时满足这三条的表示。

推论 4
"机器人协作程序"这个说法听起来很抽象，但落到行为树上就变得非常具体："出发前检查可乐在位" = 给子流程加一个执行条件；"缺货就重新装载" = 增加一个恢复分支。一个自然语言描述的教训，就这样变成了一处可执行、可检查、可回滚的结构改动。

公理五：经验库会自我污染，所以两条路都必须防"分布收窄"

这是两个系统里最容易被忽略、但设计上最见功力的一处——它们都在防同一件事：经验越积越窄。

  • EmbodiRSI 的自适应采集：把失败关联到具体配置，让困难区域获得更多采样。但必须保留一部分原始采样范围，否则数据会全部集中到少数局部情况，策略在"容易的地方"反而退化。
  • InstAgent 的经验库：修改必须通过结构与接口检查、再重新执行验证，而且经验是"行为树 + 文档"成对保存——文档里明确写着任务目标、所需能力、适用条件、失败背景、修订原因。这不是为了好看，是为了让后续任务能判断"这条经验还适不适用"。
公理链收口：载体决定能否保留（公理一）+ 失败必须归因到层（公理二）+ 自进化需要可失败的场（公理三）+ 程序需要可编辑的结构（公理四）+ 经验必须防污染（公理五）= 「EmbodiRSI 改参数 / InstAgent 改程序」不是两个并列的项目，是同一个 RSI 命题在两种失败类型上的两个必要分支。只做一层，就有一半的失败永远修不好。

How怎么拆：一个闭环 + 一次改流程

EmbodiRSI：把"采什么数据"交给当前策略的失败来回答

流程是一个四段的循环，每一段的输出都是下一段的输入：

  1. 建场：根据目标工作区与任务要求，从真实场景重建一个可执行的仿真环境，生成并验证初始示范；
  2. 跑：策略在这个仿真里执行，暴露问题；
  3. 纠错 + 定向采集（下面详述）；
  4. 训练：累积轨迹经价值模型标注后用于继续训练，更新后的策略再次执行，产生新的失败分布——所以下一轮采集的重点也变了。

注意第 4 步那句话："策略与采集分布一起迭代"。这是这套闭环和"多采点难例数据"的本质区别——难例的定义是跟着策略走的，不是人预先划定的。

两个机制分工也很清楚，一个管"单次"，一个管"多次"：

机制处理什么怎么做
协同纠错一次执行中的偏差结合多视角图像 + 动作历史 + 仿真状态判断是否需要介入；物体已经移位，就按当前物体姿态和机器人状态重新规划后续动作；纠正后成功完成的轨迹进训练集
自适应数据采集多次执行中反复出现的薄弱配置汇总失败记录 → 把有足够证据的失败关联到物体或目标的配置 → 调整下一轮示范采样；困难区多练，但保留部分原始采样范围

协同纠错这一环最值得记的是它产出了什么："补充策略实际犯错后需要的动作监督"。人（或自动判据）在机器人跑偏之后把它救回来，这条"从错误状态回到正确路径"的轨迹被记录下来——而这恰好是示范数据里永远不会出现的东西。

结果对照做得很干净：两组在办公桌 + 家居桌两个场景，数据量都控制在每子任务 400 条仿真轨迹，策略架构与训练配方完全一致。唯一变量是"静态按原分布采集"还是"纠错 + 定向采集"。答案：59.3% vs 79.9%，差 20.6pp。

这 20.6pp 在说什么
它说的不是"数据越多越好"，而是"同样预算下，数据从哪里来"决定了效果。同样 400 条轨迹，随机跟着示范分布采，和"盯着当前策略会摔的地方采"，差了 20 个百分点。这是"数据选择"作为一等公民的最好证据。

InstAgent：一次真实的意外，变成一条可复用的规则

这部分的故事线非常清楚，值得完整走一遍，因为它是"程序自进化"的最小完整案例。

场景：几台机器人接力，把人带到工位，再送一罐可乐。G1（人形）负责交互与引导，ALOHA（双臂）负责装载可乐，Go2（机器狗）负责导航与运输。

意外：研究者专门设了一次异常——可乐已经装好，但在 Go2 出发前被测试人员取走。Go2 到达目的地后，测试人员通过网页反馈：可乐没有送到。

诊断：InstAgent 回查观察记录（靠共享记忆汇集各机器人的画面、描述、位置、时间），定位到问题不在抓取、不在运输，而在装载与出发之间漏了一次确认。

修改：出发前和交付前都要检查可乐是否在位；发现缺货就重新装载。

验证与固化：候选修改先通过结构与技能接口检查，再重新执行验证交接条件与任务结果；通过后以行为树 + 经验文档成对保存。

改动在结构上是什么样？文章说得很直白：

"补上载物检查" = 给子流程增加执行条件。

"缺货后重新装载" = 增加恢复分支。

系统也可以调整不同子流程之间的先后关系。

这里有个关键点被反复强调：机器人原有的装载、导航技能一个都没变。改的只是"组织这些技能的程序"。这正好回到公理一——同一个改进，写进程序而不是写进参数，所以它可以被人读懂、被审查、被回滚，并且精确地只作用于"送可乐"这件事。

结果对照：三组都允许当前任务内恢复与重试，分别是不使用跨任务经验、复用固定经验库、复用保留了有效修订的经验库。结果是保留修订的三组模型成功率都更高。20 项任务各重复 2 次，每模型每配置 40 次；经验库在评测前准备好并冻结，测试任务没有用于建库——这个细节很重要，它排除了"经验库偷看了考题"。

合起来：那条分层判据怎么用

文章最后一节把两个系统收到一起，给出了一个可以直接拿去用的判断流程：

观察到的现象坏在哪层该做什么用哪个系统
抓取时失手、滑落，同一位置反复失败技能层在这个失败配置上多练，补错误后的动作监督EmbodiRSI
每一步都做对了，但中间漏了一次检查编排层给子流程加执行条件 / 加恢复分支InstAgent
改完之后不知道好没好验证层模型侧关掉外部纠错测策略本身、同等数据预算对照；Harness 侧固定模型与技能，区分"临时补救"与"可复用改进"两者都要

最后那行最容易被略过，但它是整套方法的可证伪性保障：要证明"改进来自这里"，必须把其他变量都钉死。这话说起来简单，做起来是这篇最硬的部分——因为"改动后表现变好"几乎总是有很多种解释。

Worth价值与局限：判据比系统值钱，而 20.6pp 到真机只剩 8.1pp

它真正讲清楚了什么

1. 把"自进化"这个词从一个动作拆成了两个，并且给出了判定该用哪个的方法。"先分清坏在技能还是坏在编排"——这一条不依赖他们的任何代码，明天就能用在任何机器人系统的排障上。这是全文最有迁移价值的部分。

2. 59.3% vs 79.9% 这组对照的实验设计非常规范。同场景、同轨迹预算、同架构、同配方，唯一变量是"数据从哪来"。这是"数据选择 > 数据数量"这个论断目前最干净的一份证据。

3. 一次真实的意外被完整走通了"诊断 → 改结构 → 验证 → 固化成经验"的全流程。而且改动落在"加一个执行条件"这种极其具体的层面，不是"让它更聪明"这种空话。这种颗粒度的案例，比任何架构图都更能说明"程序自进化"到底长什么样。

4. 两个系统都在防"经验污染"，这一点很少见。EmbodiRSI 保留部分原始采样范围、InstAgent 强制经验文档记录"适用条件与失败背景"——它们都意识到"积累"和"收窄"是同一件事的两面。

需要打问号的地方

  1. 20.6pp 是仿真成功率，真机上只剩 8.1pp——sim-to-real gap 吃掉了六成收益。仿真 59.3%→79.9%，真机对照 75.0%→83.1%。这两个数字不是同一件事：真机那组是"400 条仿真+10 条真实" vs "200 条纯真实"，比较的是采集方式，不是纠错机制本身。所以严格来说，"纠错能带来 20pp 提升"这个结论只在仿真里成立，真机上没有对应的对照实验。这是全文最大的证据缺口。
  2. "同等数据预算"只对齐了轨迹条数，没对齐采集成本。400 条仿真轨迹确实不等于 400 条真机轨迹（后者贵得多），但从真实场景重建一个可执行仿真环境的成本被完全省略了。如果每个新工位都要重建一次场景，这笔工程成本可能比采 200 条真机示范更高——而这正是团队自己说的核心痛点（"换一个工位"）。论文没有回答"换工位时多久能建好场景"这个问题。
  3. InstAgent 的结论本质上依赖"人在回路验证"。"保留修订的经验库更好"——但修订是通过结构与接口检查 + 重新执行验证过后才入库的。所以这等于说"验证过的修改是有效的"，这句话几乎不需要实验证明。真正该问的是：系统自己判断"哪个修改有效"的准确率是多少？需要人介入的比例是多少？这两个数字论文里没有。
  4. 40 次试验的粒度太粗。20 项任务各重复 2 次，每模型每配置共 40 次。这意味着成功率的分辨率是 2.5%，而且"每项任务只重复两次"根本不足以估计单任务方差。三组系统之间的差距如果小于 10pp，这个实验是分辨不出来的。文中只说了"后者成功率更高"，没给具体数字和区间——这个模糊本身值得注意。
  5. 两个系统的验证范围都窄，作者自己承认了。EmbodiRSI 只在特定桌面场景（办公桌、家居桌）验证；InstAgent 只在"固定机器人团队"（G1 + ALOHA + Go2 这个三人组）里复用。"跨机器人组合的程序迁移"被明确列为未验证。而"迁移到另一组机器人"恰恰是行为树路线最该有优势的地方（图结构应该比权重好迁），这个优势现在完全没有证据。
  6. "两层同时出问题"这个最真实的情况没有被测。文章自己也说"真实故障也可能同时涉及两层，需要分别验证改进是否有效"。但实验里两层是分开验证的。现实中一次失败几乎总是混合成因——抓取偏了 2 厘米，导致后面检查时误判"没有可乐"，然后重新装载又失败。这种级联失败，两层机制怎么协同，没有答案。
  7. 这是一篇"研究进展"而不是完整论文，商业色彩要打折看。文章后半段是公司介绍、融资情况（近千万美元种子轮）、创始人背景。两个系统的技术细节各占一节，篇幅明显压缩——比如协同纠错里"结合多视角图像、动作历史、仿真状态判断是否需要介入"这句，具体判据是什么？是规则还是学出来的？没有展开。这类关键实现细节的缺失，会让复现变得不可能。
  8. "RSI"这个词用得比实验支撑的更重。递归自我改进的严格含义是"系统改进自己改进自己的能力"——即改进能力本身也在提升。而这里展示的是"反馈 → 修改 → 验证 → 固化"的单层循环，跑了多轮，但没有证据表明"第二轮比第一轮更会改"。把它叫"持续改进闭环"完全成立，叫 RSI 就有点超前了。

一句话收尾

这篇最值得带走的不是那两个系统，是那张三层判断表：技能坏了补数据，编排漏了改程序，改完不知道好没好就钉死其他变量重测。这三句话把"自进化"从一个笼统的口号，拆成了三个可以分别执行、分别验证的动作。至于 59.3% → 79.9% 那条曲线，它在仿真里是干净的，在真机上却只剩 8.1pp 的影子——这提醒我们：这条路上每一个"提升"都要问一句"在哪测的"。而"先分清坏在哪一层"这条判据，恰恰是唯一不受 sim-to-real gap 影响的东西。
