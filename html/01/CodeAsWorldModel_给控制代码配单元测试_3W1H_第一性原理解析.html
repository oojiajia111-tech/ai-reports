一句话 让智能体自己写一个仿真器，用来给自己的代码跑测试
💡 第一性原理核心立论

LLM 几秒就能写一版机器人控制代码，真机测一次却要几分钟，还消耗硬件、承担风险——真实世界评估成了整个闭环的瓶颈。五次试验全成功，在 95% 置信下只能说明成功率高于 55%；一个版本只测一次，只能说明高于 5%。这篇的做法是让 Coding Agent 根据少量真实试验自己写一个几百行的 Python 世界模型，当作部署前的单元测试。它在 34 个程序上的预测成功率与真实结果相关系数达 0.974，能抓出"第三次试验 96%、第四次掉到 16%"这种被五次成功掩盖的回归，还能在不增加任何真实试验的前提下把无人机任务从 76% 提到 95%。关键不是绝对预测准，而是排序对。

What是什么：把世界模型当作代码测试环境

先看清对象。前沿语言模型已经开始写机器人控制器：在 RoboDojo Sim 上，Claude Fable 5.2 得分 64.9%，GPT-6 Astra 29.8%。Code as Policies 让 LLM 把控制器写成代码、在真机上跑、按结果改；ASPIRE 进一步扩展成能自主发现技能的智能体。但当模型改代码的速度远快于机器人跑测试的速度，整条流水线就堵在评估这一环。

本文提出的问题是：一个通用 Coding Agent 面对未知物理系统、手里没有现成测试环境时，能不能用少量真实试验，在自己的 Harness 里搭出一个测试环境？

所谓"验证"，就是在部署前先用世界模型跑一遍程序，对成功概率做一个经验估计。做法是让智能体把一个独立的、14–26 KB 的 Python 文件当作世界模型——里面有动力学方程、碰撞规则，以及根据观察日志拟合出来的摩擦、质心、风场等参数。

实验覆盖八项任务，横跨四种模拟器（VizDoom、PyFlyt 四旋翼、pymunk 平面推动、MuJoCo 电缆），按"测试带来的帮助从小到大"排列：

  • 无人机沿两条固定路线穿峡谷（受损旋翼 + 隐藏风场）
  • 电缆布线（隐藏刚度、摩擦、实时载荷）
  • 随机敌方火力下在 Doom 中生存
  • 推 T 形方块，再推没见过的 L 形方块（质心被秘密移动）
  • 无人机峡谷任务 + 每回合随机出现 7–8 架其他飞行器
  • 把绳子抛过立柱（可变形、每次只能试一次、对微小变化极敏感）

两个智能体对比：CaP 智能体每次真实试验后改控制程序；World Model 智能体先写世界模型，在部署前用模型筛程序。两者都用 Claude Opus 5.5，最多 5 次真实试验，只看仪器手册和自己的试验日志。

Why为什么：小样本真机测试几乎证明不了什么

五次全成功，其实什么都没说

作者开篇给了一个很不客气的统计事实：连续五次试验都成功，在 95% 置信水平下只能推出真实成功率高于 55%；如果这五次分散在多个连续版本上、每个版本只测一次，那一次成功只能说明成功率高于 5%。

LLM 在代码和数学上厉害，一个关键原因是输出可以被自动验证（跑测试、对答案）。机器人控制代码此前没有这样的验证器。

一次真实的翻车：最佳版本已经出现，却被抛弃

Push-T 任务里，方块的质心被从标称位置 (0, 45) 偷偷移到 (24, 30)。如果规划器还相信标称物理，成功率 0/20。

作者给智能体五次真实试验来推断这个变化。结果是：

试验轮次该轮生成程序的真实成功率（50 个未见 episode）
第 3 次后96%（峰值）
第 4 次后16%

而智能体最终部署了第 4 版——因为在它自己测过的那五次里全部成功。事后在它实际测过的五个随机种子上重跑，这个版本只解决了其中一个；另外四个是更早版本成功的。

这不是偶发：Mission C 中各版本成功率在 9%–87% 之间波动；Push-L 六次试验后达到 78%，下一次改代码又掉到 36%。
成功率不会单调上升，最好的版本可能早就出现，但智能体认不出来。

为什么不能直接用模拟器

用现成模拟器当测试环境当然可以，但会有循环论证：环境构建者写的模拟器，和执行任务的智能体之间信息不隔离，而且评测用的随机种子往往和开发时见过的一致。作者做了严格隔离：

不透明环境（Opaque Environments）对执行智能体隐藏全部源代码，由另一个独立智能体构建；执行方只能通过一个由仪器手册记录的精简 API 交互。还有 Import Guard：世界模型一旦试图导入模拟器或环境程序包，测试直接失败。环境里被植入了手册未披露的异常——旋翼受损、质心偏移、横风、方块释放后滑动、电缆刚度与阻力变化。评估用观察阶段从未见过的随机种子，再用第三组种子独立重测。

核心洞察：既然真实试验太少、现成模拟器又不可用，那就让智能体自己从观察数据里把一个近似测试环境写出来。它不必精确复现物理，只要能正确给程序排序就够了——这正是单元测试的本质。

How怎么做：观察 → 写模型 → 跑测试 → 部署

① 主动观察：先决定该看什么

World Model 智能体在行动前会主动决定观察什么。两个典型例子：

无人机 Mission C：悬停 19.4 秒，只看不动
第一次真实试验完全用于观察——它在起点悬停完整个试验周期，记录所有其他飞行器的轨迹。然后才改控制器。
Push-T：两次预设推动，定位隐藏质心
两次探索性推动后，模型估计质心为 (24.1, 30.0)，真实值 (24.0, 30.0)，误差 0.1；而 CaP 智能体估计约 (3, 44)，差了约 25 个单位。

这就是主动系统辨识：先探索，再利用。手册里没有的隐藏参数，被显式写成模型参数并从日志里估计出来。

② 把世界写成 14–26 KB 的 Python 文件

模型内容根据具体任务各异：四旋翼任务包含受损旋翼（只能产生正常推力的 60%）、两处横风（加速度约 14.8 和 11 m/s²）；Mission C 里智能体根据观察轨迹写出四种飞行器行为类型——沿峡谷往返、横穿峡谷往返、随机航点游走、被干扰后主动接近，还把生成位置区间设得比实测略宽。电缆任务则是 20 节点弹簧-阻尼链，13,870 字节。

值得注意的是它发现了什么：除追踪型飞行器外，其他飞行器都保持在 1.6–3.6 m 高度。于是它设计了一条 4.8 m 高度的路线，在每个检查点陡峭下降。模型内测试从 22–37% → 78–84%（仅改高度）→ 94%（加避障与调参），真实部署 Held-out 98%，重测 95%。

③ 用测试筛选程序：相关性 r = 0.974

收集所有任务里 CaP 生成的 34 个程序，让一个事先没见过它们的世界模型逐个评分。结果：

指标数值
平均绝对误差5.2 个百分点
Pearson 相关系数r = 0.974
Drone A / C / Push-T / Doom / Push-L0.6 / 4.2 / 5.1 / 5.1 / 10.1 pp

Push-L 最差（MAE 10.1pp，最大误差 22pp），但仍然跟踪住了版本间的变化趋势：真实 98% 的版本预测 97%，真实 20% 的版本预测 25.5%。绝对校准有偏，相对排序稳定。

计算成本几乎可以忽略：推动任务里 15 个程序的 3,000 次模拟 Episode 只用 19 秒；Push-T 调规划器跑了约 1.73 亿个模拟步骤。这就是把开销从"真实试验"搬到"计算"。

④ Real-to-Sim-to-Real：零新增真实试验也能迁移

把已经建好的世界模型交给 CaP 智能体，让它在大量模拟 Episode 里验证每个版本，全程不再增加真实试验：

任务起点（已耗真实试验）模拟搜索结果（零新增真实试验）
无人机 Mission C76%（20 次）22,650 个 episode / 157 秒95%（两组种子都是 95%）
Push-L46%（8 次）20,800 个 episode / 249 秒84%（重测 80%）

Push-L 上，Oracle Planner（有真模拟器）是 80%，两个智能体单独跑分别是 46% 和 72%。CaP + 世界模型的组合超过了两者各自，也超过了 Oracle。两次测试都抓到了同一个问题：CaP 最后一次根据真实结果做的修改，其实让程序变糟了。

还有一条省到极致的记录：公布一条新无人机路线、不提供任何额外真实试验，智能体复用已有世界模型，19.5 秒搜索找到成功率 100% 的控制器。

⑤ 什么时候测试没用：反馈信号已经足够

电缆布线任务是个重要的反例。系统实时提供载荷读数，超过 10 N 就失败。CaP 智能体从第一版就写了反应式规则：载荷低于 4 N 全速、7 N 停止、8.5 N 后退，最终 Held-out 50/50。

更狠的对照：删掉全部 10 个历史 Episode 日志、只给 200 张静态快照，新 CaP 智能体靠实时读数仍做到 47/50（94%），且没有过载。让任务变简单的不是免费日志，而是实时反馈。

此时世界模型无法再提升成功率，但仍能发现普通程序 Bug：对 23 个程序评分 MAE 5.2pp、r=0.980；对三个 CaP 版本在 150 个 Episode 上的预测全部正确（150/150），连失败的具体种子都指出来了。五次真实试验全成功，掩盖了 6–12% 的失败率，而模拟测试把它们挖了出来。

适用条件（作者总结）：当① Episode 存在随机变化、② 物理系统含未告知的隐藏变化、③ 控制器无法靠实时信号自我纠正，三者同时成立时，这类测试价值最大。
反过来说，只要任务提供了定义成败的实时反馈，世界模型就从"必需品"降级为"查 Bug 的工具"。

Formula关键公式：把"验证"写成可计算的对象

① 小样本的置信下界：为什么五次成功没用
\[ \Pr(\text{all }n\text{ succeed}\mid p) = p^{\,n}, \qquad p_{\text{low}} = \alpha^{1/n} \]
\(p\) 是真实成功率，\(n\) 是连续成功次数，\(\alpha=0.05\) 对应 95% 置信。
\(n=5 \Rightarrow p_{\text{low}} = 0.05^{1/5} \approx 0.55\)——五次全成功只说明成功率大概率高于 55%。
\(n=1 \Rightarrow p_{\text{low}} = 0.05\)——一个版本只测一次，成功一次只说明高于 5%。
这就是全文的问题起点：样本量的信息量随试验次数线性消耗，而 LLM 生成版本的速度是指数级的。
② 世界模型作为近似验证器
\[ \hat{p}(h) = \frac{1}{N}\sum_{i=1}^{N} \mathbb{1}\big[\,\mathcal{W}_{\theta}\big(h,\xi_i,\theta_i\big)=\text{success}\,\big], \qquad h^{*}=\arg\max_h \hat{p}(h) \]
\(h\) 是候选控制程序，\(\mathcal{W}_\theta\) 是智能体自己写的 Python 世界模型，\(\xi_i\) 是随机 episode 初值，\(\theta_i\) 是扰动后的模型参数副本，\(N\) 可达数千。
为什么要扰动 \(\theta\)：模型本身是拟合出来的、必然不准。用参数略有差异的多个副本测试，才能筛出对模型误差不敏感的程序——这是把 Sim-to-Real gap 当成鲁棒性问题处理。
筛选目标是 argmax（排序），不是 \(\hat p\) 的绝对值：实测绝对成功率会高估（Push-L +28pp，绳子 100% 对 32%），但排序仍保持。
③ 系统辨识：把隐藏物理写成显式参数
\[ \hat{\phi} = \arg\min_{\phi} \sum_{t} \big\|\, o_t - \mathcal{W}_{\phi}(s_t,a_t) \,\big\|^2 \]
\(\phi\) 是手册没写的隐藏参数（质心、旋翼效率、风场、摩擦、刚度），\(o_t\) 是观察试验里记录的状态。
实测精度：Push-T 质心估计 (24.1, 30.0) 对真值 (24.0, 30.0)；Push-L 质心 (23.4, 55.6) 对 (23.0, 55.5)，摩擦估 0.4 对真值 0.36。
但模型有明确的失效边界：电缆工具被立柱卡住再突然挣脱时，模型预测载荷 7.3 N、真实 21 N——短时域预测准（5 步误差 2.8 mm），长时域和突变事件仍不可靠。

Worth价值与局限

核心价值：它给"LLM 写机器人代码"这条路线补上了缺失的一环——自动验证。世界模型不必是训练出来的大神经网络，一个根据几次真实试验即时拟合、几百行的 Python 文件就够当单元测试层。真正的收益不是预测得多准，而是把昂贵的真实试验换成便宜的模拟排序，从而认出哪个版本才是最佳，并抓住被小样本成功掩盖的回归。

诚实的局限

局限一：绝对成功率会系统性高估
Push-T 高估 17pp，Push-L 高估 28pp，Doom 高估约 1.6 倍；绳子任务第一个控制器模型预测 100%、实际只有 32%。这个验证器只能用于排序，不能用于承诺性能——作者自己用词是"近似验证器"。
局限二：全部实验在模拟器里，没有真机
所谓"真实试验"是在 VizDoom、PyFlyt、MuJoCo 等模拟器里跑的，隐藏参数由环境构建团队植入。真机上的传感器噪声、硬件延迟、非建模摩擦能否被同样几百行代码覆盖，完全没有证据。这是从仿真到真机之间最关键的一步跨越，本文没做。
局限三：String / Push-L 上的排序能力仍不稳
Push-L 是 34 个程序里表现最差的（MAE 10.1pp，最大误差 22pp）；绳子任务几乎所有程序成功率都在 0–2%，根本没有区分度，无法评价验证器好坏。"r=0.974"这个漂亮数字被一个简单任务和一个无区分度任务稀释了。
局限四：CaP 的最优程序本来比 World Model 的更好
作者如实报告：CaP 生成的最佳程序得分高于 World Model 智能体自己的控制器——Push-T 96% 对 82–90%，Push-L 78% 对 66%。世界模型的贡献是"选对版本"，不是"写得更好"。把这两件事分开看，才不会误读它的价值。
局限五：复现材料齐全，但 Harness 还没被别人跑通
代码、全部程序和世界模型、实验日志都公开（MIT License），有 reproduce.py 可重放冻结控制器，数据也发在 Hugging Face。但作者明确说提供的小型 Harness "目前尚未有模型通过该 Harness 运行"——通用性声明还没有第三方验证。

批判性审视

  • 最有力的一张图不是方法对比，而是 CaP 的成功率曲线：72→90→92→96→16→16→96→96（Push-T）。它说明在 LLM 迭代代码的场景里，"最后一次修改 = 最好版本"这个默认假设是错的。哪怕不用世界模型，只要保留全部历史版本并做交叉验证，就能挽回一大截。
  • 实测统计口径存在"事后挑选"风险：34 个程序的排序实验用的是 CaP 生成的所有版本，但世界模型在 Push-T 上曾从一个程序的 docstring 里看到过 10/50 的 Held-out 结果——作者披露了，严格来说这是一个信息泄漏点。
  • 世界模型由同一个 LLM 写，存在同源偏差：控制器和仿真器都出自 Claude，若它对某类物理有系统性误解，测试环境会忠实复现这个误解，"自测自"可能给出虚假的安心。本文用独立构建的环境部分缓解了这点，但模型本身的同源性没隔离。
  • 电缆任务是个诚实的"反例"，也是价值边界：三个智能体都靠实时力读数轻松过关，世界模型完全不必要；它能做的只剩查几何 Bug。这提醒我们：先问控制器有没有实时纠错信号，再决定要不要建世界模型。
  • 最该抄走的一条：给 LLM 写的代码配一个可自动运行的验证器，是整个领域从"能写代码"走向"能可靠部署"的必经之路。世界模型只是验证器的一种实现；如果任务本身有廉价真值信号（力、接触、视觉成功判据），先直接用它，别急着写仿真器。
