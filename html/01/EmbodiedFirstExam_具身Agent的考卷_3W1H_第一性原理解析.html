一句话 现有机器人基准测的是"学好的策略"，编程智能体需要一套新考卷
💡 第一性原理核心立论

现有机器人基准几乎都是围绕视觉运动策略学习构建的——模型从固定动作空间里选动作，接口是死的。但 LLM 驱动的编程智能体要自己决定怎么控制机器人：直接输出动作、写代码控制、还是在仿真里训一个策略。这三种方式的能力边界完全不同，用老基准测它，等于把考卷发错了。
Embodied First Exam（EFE）因此重建了考卷：47 种机器人、1,156 项任务，每项任务跑最多三种设置——Privileged（可读全部状态、可无限重置，近似上界）、Standard（只有传感器观测、不能重置）、Realtime（环境持续运行不许思考）。结果是扎心的：在 391 项配对任务上，最强的 GPT-6 Astra 在 Privileged 下解掉 77%，到 Standard 只剩 30%。而受控实验给出关键洞察：给智能体重置环境的帮助，大于给它物体精确状态（53% vs 45%）；且在"精确操作"阶段，精确状态几乎无用，重置却能多解 16%。

What是什么：一个"考试"，考的是编程智能体不是策略

先看清被讨论的对象。Embodied First Exam（EFE）由 MLL Lab（东北大学）提出，是首个面向 Agentic Robotics 的统一评估框架。规模上它很大：47 种机器人、35 个任务套件、1,156 项任务，其中 9 个是新建套件、26 个从现有基准适配而来。

它的定位是"编程智能体进入物理世界之前的第一场考试"。但更关键的是它与现有基准的根本差异：

现有机器人基准（如 VLA 类）Embodied First Exam
被测对象已学好的视觉运动策略未经修改的通用编程智能体
动作从哪来从基准定义的固定动作空间中选智能体自己决定：直接控制 / 写代码 / 训策略
接口观测 → 动作，固定 IO读接口文档、选控制方式、执行、再调整
怎么算分环境内置判定独立容器的验证器重放智能体提交的轨迹或控制器

三条设计原则撑起整个框架：

  1. 纳入超越抓取与放置的多样化任务——空间谜题、灵巧操作、多机器人交互、动态全身控制、Sim-to-Sim 工程
  2. 衡量物理约束如何影响成功率——每项任务最多三种评估设置
  3. 为不同模型、Harness、控制方式提供统一基础设施——一条命令跑任意组合

工程上它基于 Harbor（Terminal-Bench 的评估框架）：任务在容器里跑，智能体有自己的工作区（可装包、写代码、训模型），验证器在智能体容器之外，只接受智能体提交的答案。

Why为什么：机器人获得技能有三条路，基准只测了第三条

原文的切入点是机器人获得新技能的方式分类：

路线一：人工编程
工程师直接写控制代码。灵活但不可规模化，且写不出通用性。
路线二：从数据中学习
近期的 VLA、世界动作模型（WAM）。这是现有机器人基准的主战场，也是问题所在。
路线三（本文焦点）：LLM 驱动的编程智能体
智能体把指令翻译成可执行代码，并通过自动化实验调整计划；可以自己选择：直接控制机器人、写机器人程序、或者训练策略。Agentic Robotics 的早期成果表明这可能是范式转变——但能力边界仍是开放问题。

于是论文要回答三个问题，而现有基准都答不了：

  • 通用编程智能体能解决哪些机器人任务？
  • 它们需要遵守哪些物理世界约束？
  • 又会在哪里失败？
现有基准答不了的根本原因：无法仅凭一组范围有限的机器人任务，或不施加物理世界约束的自动编程任务，确定能力边界。要回答它，需要明确该评估哪些机器人能力、物理约束如何影响成功率、并通过任务接口支持不同的模型和 Harness。

三种评估设置：把"物理约束"变成可控变量

这是全文最核心的设计。同一任务，三种设置，共享初始场景、成功规则、时间限制，结果天然配对：

设置智能体能做什么模拟什么现实
Privileged与仿真器同容器，读全部仿真状态，无限次重置，可试错搜 Oracle 解性能近似上界，也可用来生成训练数据
Standard仿真器作为独立服务，只能通过 API 查本体状态、取标定 RGB-D、发动作块；默认不能重置；请求间仿真暂停真实机器人条件——只有传感器观测、无重置、无实时压力
Realtime同 Standard，但仿真持续运行不暂停（按实时速度固定比例）真实部署的实时性压力
一个关键的克制：论文明确指出这个上界是针对一组任务，而非每一项单独任务——因为智能体可能在 Standard 下解出某项任务，却在 Privileged 下失败（附录 D）。这说明三种设置不是简单的难度阶梯，它们的失败结构不同。

How怎么做：三种控制方式 + 阶段级失败标注

控制方式由智能体自选

给定自然语言任务指令后，智能体可以自行决定怎么干：

  • 直接控制（Direct control）：接收观测后直接输出动作
  • 编写代码进行控制（Code to control）：输出规划器、控制器或其他程序，由程序生成动作
  • 训练策略进行控制（Train a policy）：在仿真中训练策略并用它控制机器人

框架只约束结果，不约束手段——这与"预固定控制方式"的既有 Agentic Robots 研究完全不同。

资源约束（这才是真实感的关键）

每项任务都设：智能体的时间限制与 token 预算、机器人的重置预算、某些任务的步数限制、以及 CPU / 内存 / GPU 显存 / 磁盘上限。9 个套件提供重置预算，次数 3~50 次。

值得注意的是：token 预算足够高，从未有任何一次尝试触到上限——说明当前的瓶颈不在推理预算，而在别处。

阶段级失败标注：把"失败了"变成"在哪一步失败了"

验证器只判通过与否，不指出错在哪。于是论文引入任务图：把任务划分成多个阶段，每个阶段对应一次必需的环境状态变化。

例子：「将番茄放入关闭的冰箱」= ①冰箱被打开 → ②番茄被放入冰箱 → ③冰箱再次关闭。
阶段有类型（共九个类别：Relation / Dynamic / Body / Competition / Material / Mechanism / Contact / Precise 等）和所需接触标注。
失败阶段判定规则：一次失败尝试最多对应一个失败阶段——若发生跌倒等不可逆事件，取该事件所在阶段；否则取智能体未能纠正的最早错误所在阶段。注意失败可能发生在前置条件满足之前（"智能体可能在打开冰箱之前就把番茄掉了"）。

标注由编程智能体完成（GPT-6.1 Sol 写大多数、Claude Sonnet 5.5 写其余，Claude Sonnet 5.5 审核全部），共分析 8 个智能体在 427 项任务上的失败尝试。

核心任务集

1,156 项任务里挑出 456 项困难任务组成核心集（901 项测试）。筛选规则：排除判断为简单的、排除初筛智能体 GPT-6 Luna 已解决的，但保留各套件作者要求保留的。

论文自己承认的筛选偏差：由于 GPT-6 Luna 与 GPT-6 Astra 属同一模型家族，这种筛选可能使核心任务集偏向排除该模型家族能解的任务。——这是很诚实的自曝。

Formula关键公式与判据

① 三种设置的权限差异
\[ \begin{aligned} \text{Privileged} &: \quad \text{state}_{\text{full}} \;\oplus\; \text{reset}^{\infty} \\ \text{Standard} &: \quad \text{obs}_{\text{sensor}} \;\oplus\; \text{reset}^{\le B} \\ \text{Realtime} &: \quad \text{obs}_{\text{sensor}} \;\oplus\; \text{reset}^{\le B} \;\oplus\; \text{wall\_clock}_{\text{real}} \end{aligned} \]
\(\oplus\) 表示"可获得的资源集合"。
Standard 与 Realtime 的唯一差别是最后一项：仿真是否在智能体动作之间暂停。
Privileged 的定义性特征是 \(\text{reset}^{\infty}\)——无限重置，也就是可以试错搜 Oracle 解。
消融的三个条件（第 3.2 节）：① 只给精确状态；② 只给重置；③ 两者都给；④ 基线＝仅隐藏成功信号（不增加任何能力，用来估计"再来一次"的收益）。
② 失败阶段集中度（Failure-Stage Concentration）
\[ C = \frac{\#\{\text{两两配对的失败尝试落在同一阶段}\}}{\#\{\text{全部两两配对}\}} \]
基线构造：随机抽取每次失败所处的阶段，各阶段被抽中的概率取自同一设置下其他任务的失败分布。
实测：三个最强智能体在 Standard 下集中度 56%，随机基线 31%——高出 25 个百分点，说明失败位置有系统性结构，不是随机噪声。
跨设置一致性：排除"两种设置下最常见失败阶段均为第一阶段"的任务后，仍有 57% 的任务在 Privileged 与 Standard 下最常见失败阶段相同，随机基线仅 9%。
③ 阶段失败率与阶段类型划分
\[ \text{FR}_{\text{type}} = \frac{\#\{\text{在 type 类阶段失败的尝试}\}}{\#\{\text{到达过 type 类阶段的尝试}\}} \]
精确操作阶段：需要紧密配合、到达目标位姿或路径、或与运动物体接触
粗粒度阶段：只需到达某区域或容器、完成抓取、或改变机构状态
关键实测：从 Privileged 降到 Standard，精确操作阶段失败率上升 24~46 个百分点，粗粒度阶段只上升 1~20 个百分点。
例：组装阶段 34% → 80%，放置阶段 23% → 35%。
阶段类别失败率（合并两种设置）：Material（擦拭等改变材料状态）66% > Body（行走等移动身体）45% > Mechanism（开门等）20%。
④ 四个受控实验的结论汇总
实验条件GPT-6 Astra 在 391 项配对任务上的 Standard 成功率
基线什么都不加28%
加精确状态可查询每个物体的精确状态45%
加重置可保存状态的无限次重置53%
两者都加—68%（Privileged 上界为 77%）
推论：允许重置时，66% 的成功发生在从已保存状态开始的 episode 中——智能体可以只重试困难阶段，不必从头重复整个任务。
分阶段看（91 次精确操作阶段失败）：仅隐藏成功信号可解 19%，加精确状态解 21%，加重置解 36%——精确状态几乎无用，重置多解 16 次。
粗粒度阶段则相反（97 次失败）：仅精确状态就解 34%，基线 14%。

Worth价值与局限

核心价值：这篇论文做了一件此前没人做的事——把"编程智能体控制机器人"这件事的失败结构，量化到阶段级别。三个结论极有指导性：
① 特权与真实的差距不是玄学，是可拆解的：Standard 少掉的不是"智力"，而是重置权——补上重置能多解 25 个百分点（28%→53%），补上精确状态只多 17 个（28%→45%）。
② 失败高度结构化：56% 的失败配对落在同一阶段（随机 31%），且跨设置一致（57% vs 9%）——意味着提升可以聚焦，不必全面加强。
③ 控制方式是智能体的自由选择，而这本身就是一种能力：97% 的 Realtime 尝试用写程序、82% 的 Privileged 也是、只有 61% 的 Standard 用直接控制——越接近真实越倾向写代码。而在足球任务上，只有训练出来的策略能赢（GPU 版 10:8 胜，CPU 手写步态 3:13 负）。

论文自己列的局限

局限一：每项测试只跑一次
没有置信区间，无法区分"智能体反复出现的失败"与"单次运行波动"。论文也承认：Claude Opus 5.5 与 Gemini 4 Argon 合计多解的 64 项中，有一部分可能只是运行间波动。
局限二：标注由智能体生成
阶段级标注和控制方式标注都是 LLM 做的。且负责大部分标注的 GPT-6.1 Sol 与被评估的 GPT-6 Astra 同属一个模型家族——论文自己点出这"可能使这些比较产生偏差"。
局限三：全部结果来自仿真
没有真机验证。只有附录 I 的"初步演示"（两个智能体用真实机械臂完成导线接触游戏）。论文承认 Standard 设置的接口理论上可用于实体硬件，但"我们计划通过这一接口系统地评估"，即尚未做。
局限四：Realtime 覆盖不全
因算力限制，Realtime 目前只在动态任务上评估，且是 1,489 次抽样尝试的子集统计——"97% 用程序"这个数字来自抽样，不是全集。

批判性审视

  • 核心集筛选存在家族偏差，论文已自曝但影响不小：456 项里排除的正是 GPT-6 Luna 能解的任务，而 Luna 与 Astra 同族。这会系统性抬高 Astra 的相对分数、压低其他模型的分数。也就是说"最强智能体"这个排序本身带有筛选偏好。
  • 阶段失败率的因果解释被作者自己否掉了：原文说"每个类别主要出现在特定套件中，并对应特定机器人，因此这些失败率并不能证明失败是由阶段类别本身造成的"。这很诚实，但也意味着"Material 阶段失败率 66%"这类数字不能当作通用结论用。
  • 足球任务那个对照被作者主动降级了：GPU 版与 CPU 版在多个方面不同（多了 GPU、多了 RL 库、多了训练示例），所以"仅凭这一项任务无法确定究竟是哪一项差异起了作用"。这是双盲对照该有的自觉，但结论也就只能当轶事看。
  • "重置比精确状态更管用"这个结论的适用边界要说清：它是在精确操作阶段的结论；粗粒度阶段恰恰相反（精确状态解 34%，重置作用小）。把它讲成"重置更重要"是过度简化。
  • 30% 这个数字该怎么读：456 项 Standard 测试里 GPT-6 Astra 解了 24.1%~33.6%（不同 harness），三个最强智能体合计 48%。这意味着一半以上的核心任务当前无人能解——既说明任务够难，也说明这个基准短期内的区分度会很低（大量智能体都在 0~20% 区间）。
  • 智能体标注 + 智能体被测 = 方法论上的自指：用 LLM 给 LLM 的失败做阶段归因，再据此设计改进方法，虽有 Claude Sonnet 5.5 交叉审核，但审计链条仍不够独立。
